# TALA benchmark baseline

Baseline of the unmodified engine (fork `master` = upstream `6a7b483`) on the
generated architecture corpus, with dagre and ELK for comparison. Later work
(speed, stability, quality) is measured against these numbers.

## How to reproduce

```sh
# Corpus and metric unit tests (fast, part of go test ./d2layouts/d2talalayout/...)
go test ./d2layouts/d2talalayout/bench

# Regenerate the corpus after changing the generator
go test ./d2layouts/d2talalayout/bench -run TestCorpusFiles -update

# Full table. GOMAXPROCS=1 approximates D2.js, where Go WASM runs on one thread.
go build -o /tmp/talabench ./d2layouts/d2talalayout/bench/cmd/talabench
GOMAXPROCS=1 /tmp/talabench -timeout 3m            # Markdown table on stdout
GOMAXPROCS=1 /tmp/talabench -format jsonl          # machine-readable
GOMAXPROCS=1 /tmp/talabench -cases arch_060 -engines tala -no-edit -cpuprofile /tmp/cpu.pprof

# One case as a Go benchmark (follows the engine's BENCHMARK_GRAPH convention)
BENCHMARK_CORPUS=arch_060 BENCHMARK_ENGINE=tala-1seed \
  go test ./d2layouts/d2talalayout/bench -run '^$' -bench '^BenchmarkCorpus$' -benchtime=1x
```

Machine: 4 vCPU Intel Xeon @ 2.10GHz, 15 GB RAM, Linux, Go 1.27.0,
`GOMAXPROCS=1`, single runs, 3 minute timeout per layout.

## Corpus

`testdata/corpus/arch_NNN.d2` is generated by `corpus.go` from a fixed seed.
`NNN` is the exact number of D2 objects, containers included. The diagrams look
like software architecture diagrams: clients (`shape: person`), an `edge`
container (CDN, load balancer, gateway), service domains as containers holding
api / db (`cylinder`) / worker / cache / queue / ui / scheduler / indexer
components, shared data and external (`cloud`) containers, labelled and
unlabelled edges (intra-service, cross-service calls, gateway fan-out, event
bus, third-party APIs and a webhook back-edge). Containers are nested one
level (`arch_010`) or two levels (`services.<domain>.<component>` up to 100
objects, `<area>.<domain>.<component>` from 150 objects).

Each file ends with a `# bench-edit: <src> -> <dst>` comment: the one-line edit
used for the stability metric, an edge between two existing, unconnected
leaves in different domains.

| case | objects | edges | containers |
|---|---:|---:|---:|
| arch_010 | 10 | 9 | 2 |
| arch_060 | 60 | 70 | 13 |
| arch_100 | 100 | 118 | 18 |
| arch_200 | 200 | 245 | 34 |
| arch_500 | 500 | 645 | 95 |

`arch_100` is not one of the original four sizes. It is the largest size of
this family that the unmodified engine completes (see the 200/500 rows).

## Engines

- `tala`: `d2talalayout.Layout` with the defaults D2.js uses (`DefaultLayout`:
  seeds 1, 2, 3, then the compound-candidate refinement) and
  `MaxConcurrency: 1`, because in WASM `GOMAXPROCS` is 1 and the seeds run one
  after another.
- `tala-1seed`: the same with `Seeds: []int64{1}` (D2:
  `vars: {d2-config: {data: {tala-seeds: [1]}}}`, CLI `--tala-seeds=1`).
- `dagre`, `elk`: D2's built-in Go implementations, as in D2.js.

All run through `d2lib.Compile` exactly as D2.js does.

## Metrics

- **layout ms**: time inside the layout engine callbacks (layout plus any
  `RouteEdges` callbacks D2 makes). **compile ms** is the whole
  `d2lib.Compile`.
- **crossings**: distinct points where the rendered paths of two different
  connections properly cross. Points within 1px of either path's endpoints
  (shared ports) and collinear overlaps are not counted. Curved (dagre) routes
  are flattened with 16 samples per cubic segment.
- **bends**: polylines (TALA, ELK) count every interior vertex turning by more
  than 1°. Curves (dagre) count every maximal run of same-direction turning
  totalling at least 20°, so a quarter arc is 1 bend and an S-curve is 2.
- **edge length**: total rendered length of all routes, in px.
- **bbox**: `d2target.Diagram.BoundingBox()` (shapes, labels and routes).
- **empty %**: (bbox area − Σ area of top-level shapes) / bbox area. Top-level
  shapes are root objects, containers included, so space inside containers
  counts as used.
- **edit layout ms / disp mean / disp max / moved**: lay out the source again
  with the `bench-edit` line appended. For every shape in both layouts except
  the new edge's two endpoints, measure how far its center moved (px). `moved`
  counts shapes that moved more than 1px. Raw coordinates, no alignment.

## D2.js (WASM) timings

Local D2.js build of the same commit (`wasm-opt -O2`), Node 22, one compile
per row after a warm-up compile, wall time of `d2.compile` (includes parsing,
text measurement and result serialization; render is separate).

| case | tala | tala-1seed | dagre | elk |
|---|---:|---:|---:|---:|
| arch_010 | 1192 | 400 | 48 | 65 |
| arch_060 | 24758 | 9994 | 465–918 | 256–1324 |
| arch_100 | 77364 | 32071 | 455–607 | 244–453 |
| arch_200 | not run | error after 70472 | 3087 | 736 |
| arch_500 | not run | error after 368565 | 38420 | 1499 |

TALA in WASM is about 4–4.5x slower than native single-threaded
(`arch_060`: 24.8 s vs 6.0 s; `arch_100`: 77 s vs 18.7 s). The B1 goal
(60 objects < 200 ms, 200 objects < 1 s in the browser) needs roughly 125x on
`arch_060`, and `arch_200` must first stop failing. A two-node `a -> b`
compile with default TALA takes 18 ms natively (5 ms with one seed) but
90–300 ms in WASM, so small diagrams pay a larger WASM penalty. dagre and ELK
through D2.js are also 4–10x slower than natively, and the compile result for
`arch_060` serializes to ~450 KB of JSON.

## Where the time goes

CPU profiles from `talabench -cpuprofile` (GOMAXPROCS=1, seed 1 unless noted).

Seeds and refinements: with the defaults, the three seeds are ~98% of
`arch_060`'s TALA time (each a full pipeline run); the compound-candidate
refinement and scoring are ~2–3%. One seed is 2.6–2.7x faster than three
(`arch_060` 6.0 → 2.25 s, `arch_100` 18.7 → 7.3 s), not exactly 3x, because
seeds differ in cost (see below).

Pipeline stages, one seed (engine `BenchmarkAutolayout` with stage timings,
seed 123, on the corpus graphs exported to engine JSON):

| stage | arch_060 (1.71 s) | arch_100 (4.57 s) |
|---|---:|---:|
| NodePlacement | 670 ms (39%) | 1130 ms (25%) |
| EdgeRouting (3 route flavors) | 362 ms (21%) | 1152 ms (25%) |
| SwapStuff | 225 ms (13%) | 948 ms (21%) |
| AlignAxes (4 runs) | 198 ms (12%) | 535 ms (12%) |
| GapNormalization | 155 ms (9%) | 543 ms (12%) |
| Equidistance | 57 ms (3%) | 158 ms (3%) |
| everything else (preprocess, binpack, labels, cleanup) | < 3% | < 3% |

On `arch_200` (one seed, fails in routing after 19 s) SwapStuff is 34%,
NodePlacement 16%, AlignAxes 16%, GapNormalization 14%, routing 10% before
the failure, Equidistance 5%.

Hottest functions (cumulative unless noted):

- `placementcost.EdgeLength` / `NodeEdgeLength` / `evaluateNodeEdgeLength`
  (15–21%) and `placementcost.nodeSymmetry` (13–17%): placement candidates
  rescore edge length and symmetry of whole neighbourhoods for every move.
- `routing.(*ovgEdgeRouter).search` (17% on 60, 37% on 100): A*-style search
  over the orthogonal visibility graph, run for 3 route-generation flavors
  (ShortestToLongest, LongestToShortest, Default); the best total distance
  wins. Flavors run in goroutines, so in WASM they run one after another.
- `placementcost.GraphEdgeCrossings` → `countEdgeCrossingsExcludingSharedNodes`
  → `layoutgraph.SegmentsCross` (16% on 200, 9% flat): all-pairs crossing
  counts recomputed for every swap candidate (O(E²) per evaluation).
- `layoutgraph.(*Transaction).Commit` / `isBadStateContext` /
  `doesOverlapWithDimensionsContext` (8–19%): every speculative move
  revalidates overlaps against all nodes.
- Go map lookups (`runtime.mapaccess*`, 10–12% cumulative): per-node and
  per-edge state kept in pointer-keyed maps in hot loops.
- Work-guard and context polling (`WorkGuard.checkAtStride`, `ctx.Err`): ~3–4%.

## Seeds and concurrency

- `Options.Seeds` nil uses `{1, 2, 3}`; an explicitly empty list is an
  error. Seeds are de-duplicated in first-seen order, at most 16 unique (64 raw
  entries). Diagram data `tala-seeds` (`vars: {d2-config: {data: {tala-seeds:
  [1]}}}`) overrides the option, so D2.js users can already select one seed from
  the source; D2.js itself has no seeds option and always calls
  `DefaultLayout`.
- `Options.MaxConcurrency` 0 means `min(GOMAXPROCS, 4)`, capped at the number
  of seeds; valid range 1–16. In WASM `GOMAXPROCS` is 1, so seeds run one
  after another.
- Every seed always runs to completion and the best score wins (ties go to the
  later seed), so concurrency changes only wall time, never the result:
  `arch_060` gives byte-identical shapes with `MaxConcurrency` 1 and 3. Seed 3
  wins on `arch_060`, and running only seed 3 reproduces the 3-seed layout.
- Single-seed cost on `arch_060` varies by seed, roughly 1.9–3.3 s natively
  (one unloaded GOMAXPROCS=1 run of seed 1: 2.2 s), about a third of the
  3-seed total.

## Speed levers (ranked by expected gain for the B1 goal)

Estimates are for the browser (single-threaded WASM) unless noted; "measured"
means a throwaway experiment above.

1. **Warm start from the previous layout** (also B2): keep positions of
   unchanged nodes, place only new or changed ones, reroute only affected
   edges (`RouteEdges` already exists). For a one-line edit this should be
   10–100x faster than a full layout, and it fixes stability. Large effort.
2. **Incremental placement costs**: `EdgeLength`, `nodeSymmetry` and
   `GraphEdgeCrossings` are rescored over whole graphs or neighbourhoods for
   every candidate move or swap (35–50% of time; the O(E²) crossing recount
   in SwapStuff is 34% at 200 objects). Delta scoring of the moved nodes'
   edges plus a spatial grid for crossings: estimated 2–4x at 60–200 objects,
   more at 500. Medium–large effort; changes goldens unless kept exact.
3. **One seed by default, or seeds in parallel Web Workers**: measured 2.6–2.7x.
   Running the three seeds in three D2.js workers keeps the 3-seed result at
   1-seed latency (memory x3). Trivial (one seed) to medium (workers).
4. **Routing**: one route flavor instead of three measured 1.4x on `arch_100`
   (routing-heavy), ~1x on `arch_060`. Beyond that, a smaller OVG (per
   container or coarse-to-fine), a tighter A* heuristic and a per-edge
   budget with a simple fallback instead of failing the whole layout: est. 2x
   on routing, and it removes the ≥120-object failures (B5). Small (flavors)
   to large (OVG).
5. **Placement iteration count** (`nodePlacementIterations` 90 × √n per
   container): 90 → 30 measured 1.6x on `arch_060`, 1.07x on `arch_100`. Tie
   it to a deterministic work budget / quality level that Boxwire passes
   (fast while dragging, full when idle). Small effort.
6. **Optional refinements**: skipping the compound candidate measured
   1.1–1.2x; SwapStuff 1.1–1.15x (with more crossings). Gate both on the
   quality level. Trivial.
7. **Dense indices instead of pointer-keyed maps** in hot loops (map lookups are
   10–12% cumulative natively, likely more in WASM) and a spatial index for
   transaction overlap checks (8–19%): est. 1.2–1.5x combined. Medium,
   mechanical.
8. **WASM fixed costs**: a 2-node TALA compile takes 90–300 ms in WASM vs
   5–18 ms natively; the D2.js compile response for 60 objects is ~450 KB of
   JSON. Worth profiling in the browser; est. 50–250 ms per compile. Small–medium.

Configuration-only levers (3, 4 flavors, 5, 6) measured 5.2–5.7x together
(`arch_060` 6.0 → 1.05 s native, ≈ 4–5 s in WASM). The B1 target needs about
125x on `arch_060`, so 1, 2 and the routing work are required.
